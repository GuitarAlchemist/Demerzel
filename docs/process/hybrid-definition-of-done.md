# Hybrid Definition of Done (DoD)

Related: #576, #570, #461

## Purpose

The Hybrid Definition of Done ensures that completed work—whether generated by an AI agent or a human—meets the Demerzel ecosystem's standards for quality, safety, and traceability before being merged. It establishes a clear, verifiable checklist for pull requests.

## Criteria for Completion

A pull request (PR) should not be considered "done" or ready for final merge until it meets the following criteria:

1. **Linked source issue:** The PR must reference the issue that shaped it (e.g., "Fixes #123", "Related: #456"), establishing traceability back to an issue that passed the Definition of Ready.
2. **Clear summary:** The PR description must clearly articulate what changed, why it changed, and how it aligns with the original issue's goals.
3. **Tests or validation evidence:** The PR must include proof that the change works. For code, this means test logs or CI output. For documents or schemas, it might mean the output of validation scripts (like `python scripts/validate_governance.py`).
4. **Changed-path risk notes:** A brief assessment of the risks introduced by modifying the specific paths involved, especially if crossing architectural or governance boundaries.
5. **Follow-up issues:** If the scope of the original issue was trimmed to keep the PR small and safe (a "vertical slice"), follow-up issues must be created and linked for the deferred work.
6. **Review findings resolved:** All feedback from human or AI reviewers (e.g., Skeptical Auditor) must be addressed with code changes or explicitly accepted and documented.
7. **No hidden auto-merge expectation:** AI-generated PRs must never assume they will be automatically merged, especially in high-risk areas. Asimov's Second Law requires human-in-the-loop (HITL) oversight.
8. **Human/Demerzel merge decision:** Final approval and the action to merge must be executed by an authorized human or through an explicit Demerzel governance tribunal decision.

## Non-goals and Exceptions

* **Do not require every small issue to have heavyweight ceremony.** Trivial typo fixes or minor documentation updates can use an abbreviated form of these checks.
* **Do not block urgent human decisions.** In emergencies (e.g., fixing a critical outage), humans may override the standard flow, provided a post-incident review documents the bypass.
* **Do not let missing polish stop clearly safe docs work.** If the core information is accurate and safe, a documentation PR should be merged rather than stalled over minor formatting preferences.

## Relation to the Broader Process

The DoD is the final checkpoint before code enters the `master` branch. It works in concert with:
* The **Definition of Ready** (which ensures the work was properly bounded before it began).
* The **AIW Operating Doctrine** (which requires explicit proof and limits scope expansion).
* The **Governance Resilience policies** (which require that all changes be verifiable and traceable).
